# CoinTR Fraud Journey 分析与模型面试综合报告（公开脱敏版）

> **公开边界**：本报告只复原参考 OCR/TXT 材料中可以公开复述的分析方法，并将其映射到本仓库的确定性合成数据。仓库不包含原始截图、真实用户记录、内部账号、密钥、生产阈值或外部监管报送能力。文中的历史数字是材料中的分析示例，不代表本仓库运行结果，也不得表述为个人独立上线的生产业绩。
>
> **处置边界**：模型高分、图谱关系和规则命中只能形成调查优先级或人工复核候选，不能自动改标、冻结、限权、清退或提交 STR/监管结果。

---

## 1. 项目真正解决的问题

这项 Fraud Journey 工作不是从“训练一个更复杂的模型”开始，而是从现有策略的业务缺口开始：

```text
现有策略表现与审核容量
→ 样本和标签口径
→ Fraud 用户经过什么业务路径
→ 哪些维度存在稳定差异
→ 差异能否加工成可用特征
→ Tree 能否找到可解释组合
→ XGBoost 能否改善全量排序
→ Risk Graph 能否补充团伙和关系证据
→ 如何形成线上/离线策略并进入治理闭环
```

材料中的历史基线显示，现有链上提币 Fraud 策略存在“有一定 Precision、但 Recall 很低”的问题。示例混淆矩阵为 TP 337、FP 243、FN 3,877、TN 24,438，Precision 约 58.10%，Recall 约 8%。因此首要任务是分析漏判黑用户，而不是单纯追求 AUC。

正式评价至少应包含：

- Precision、Recall、F1、PR-AUC/AP、KS；
- Lift@实际审核深度与 Alert Rate；
- 与已有策略的 Overlap、Swap-in、Swap-out；
- 新增 TP、增量 Recall、误伤人数；
- 人工审核容量、处置严重度和客户体验成本。

## 2. 黑样本、白样本与未标记用户

### 2.1 黑样本

材料中的黑样本应当是：

```text
已确认 Fraud 名单
+
此前因 Fraud 原因经调查清退的用户
-
内部 / 系统 / 做市商 / 测试 / 机构等非零售账户
```

必须保留 `label_source`、`label_observed_at`、调查状态和处置来源。没有来源和观察时间的单一 `fraud_label`，无法回答标签是否成熟、是否受到调查选择偏差影响。

### 2.2 白样本

白样本是经过业务口径维护的相对可信正常样本，不等于所有 `fraud_label=0` 用户。把全部未确认用户当干净负样本会产生标签污染，并使高分未标记用户被错误解释为“模型误报”。

### 2.3 未标记大盘用户

既不在黑名单也不在白名单的用户应保留为 Unlabelled，用于：

- 观察大盘行为分布；
- 形成高分未标记用户 Shadow 队列；
- 发现可能漏标的关系路径；
- 评价特征覆盖和数据质量。

它们不应未经人工调查全部进入负样本训练。

### 2.4 沉默用户和账户角色

完全没有入金、交易和出金行为的沉默用户，应从行为特征有效性分析中排除；这只表示缺乏本 Journey 的行为暴露，不代表一定低风险。

内部账户、做市商、测试账户、机构和 Treasury 用户可能天然具备高频 API、大额多币对交易、共享 IP、归集地址等特征。公开合成项目后续必须增加 `account_role`，否则会把合法业务模式学习成 Fraud。

## 3. 交易币对：分群信号，不是 Fraud 定义

初始材料重点关注 TRY→USDT、TRY→TRX、TRY→BTC 等主路径。进一步统计发现，约 91% 的 Fraud 用户使用过 USDT/TRY，但约 45% 同时交易其他币种，因此不能只筛选单一币对。

正确的特征设计应包括：

```text
has_usdt_try
has_trx_try
has_btc_try
main_pair_trade_ratio
main_pair_only_flag
multi_pair_flag
trade_pair_count
small_altcoin_trade_count_under_threshold
```

币对用于分群、行为画像和策略条件；只有结合 KYC、入金、交易、出金、地址和时间信号后，才可能构成风险证据。

当前仓库只有 `asset_pair_unique_count`，没有持久化每个关键币对的用户级 Flag，也没有订单买卖方向和小币种单笔金额。因此 source-aligned 覆盖审计将这部分标为 `MISSING`，而不是假装已实现。

## 4. 数据质量优先于特征工程

### 4.1 银行字段

原材料特别强调银行字段的兼容和覆盖：银行卡号可能掩码，银行代码和名称需要映射，用户名存在历史别名或拼写版本。分析前应完成：

1. canonical 字段与 legacy alias 兼容；
2. 事件级字段覆盖率和缺失机制检查；
3. 掩码卡号、用户名和银行代码联合核验；
4. 用户级聚合与原始事件计数 reconciliation；
5. 增加 `bank_feature_available_flag`，避免把“缺失”解释成“低风险”。

当前合成仓库能支持 `bank_risk_mean`、`bank_risk_max` 和 `bank_name_match_ratio`，但不能支持真实的掩码卡号关联和法币出金银行卡数量。

### 4.2 事件状态和 Point-in-Time

事件特征必须：

- 只使用当时已经可见的数据；
- 排除 `PENDING`、失败和未来状态；
- 处理同一笔业务跨状态重复日志；
- 保证特征时间早于标签成熟时间。

当前主 Demo 已过滤 `SUCCESS` 并执行 PIT 截止，但尚无业务交易键，不能完整完成跨状态去重。source-aligned 层明确把“业务键和父子事件关系”列入后续 P0。

## 5. Fraud Journey 的分析维度

### 5.1 注册与 KYC

候选字段包括注册端、注册来源、邀请关系、KYC L1/L2、注册/KYC IP 与设备差异、KYC 时长及 KYC 到首次入金时长。

小样本中出现的“无邀请人”“仅通过 L1”“特定注册来源”等现象，只能形成待验证假设；必须和白样本及大盘用户对比覆盖率、坏率和稳定性。

### 5.2 入金—交易—出金闭环

材料对少量黑用户观察到入金、交易和出金总量高度接近，因此提出两个特征：

\[
CV=\frac{SD(Deposit,Trade,Withdraw)}{Mean(Deposit,Trade,Withdraw)}
\]

以及：

\[
RangeRatio=\frac{Max-Min}{Mean}
\]

它们试图刻画资金是否快速完成“流入—转换—流出”的近似闭环。当前仓库已有 `fund_loop_cv` 和 `amount_diff_ratio`，新增分析层也按材料公式计算可比 Preview。

但必须注意：

- 单纯金额大并不等于 Fraud；
- 少数 Whale 会显著抬高均值；
- 应同时看中位数、分位数、Winsorized 统计和用户级比例；
- 生命周期累计口径与 24 小时快照不能混称同一指标。

### 5.3 速度与计数

重点包括：

- KYC 后多久首次入金；
- 入金后多久首次交易或链上出金；
- 首次若干分钟内链上出金次数；
- 入金、交易、出金次数；
- 单笔大额入金次数、小额分散入金次数；
- 不同银行卡、地址、IP 和设备数量；
- 资金在平台的停留时长。

计数类特征应同时给出是否发生、次数、占全部动作比例、时间窗口和用户活跃基数，不能只比较总数。

### 5.4 现货和 API 行为

正常交易者可能具备更多币对、连续现货交易和 API 行为。材料中的后续分析甚至发现部分白样本在连续交易和币种多样性上更高。因此 API 或高频交易不能被预设为风险方向。

本仓库把 API 和夜间活动保留为 `context-only`，不进入主 Tree/XGBoost，也不能单独转规则。

## 6. 60 分钟 Session 为什么必须先清洗

原始设想是：相邻动作超过 60 分钟即视为一次操作结束，再分析 Session 内密度。但事件表中可能包含系统自动后处理、对账、状态更新或消息事件。用户一次主动行为会立即触发多个自动事件，造成伪造的“秒级高密度操作”。

正确顺序为：

```text
原始事件
→ 只保留终态
→ 区分 USER / SYSTEM origin
→ 用 parent_event_id 或业务键折叠父子事件
→ 排除后台和被动事件
→ 保留用户业务动作
→ 再按 60 分钟切 Session
→ 计算时长、密度、多样性、序列与间隔
```

新增 `sessionize_user_events` 已实现：先过滤非终态和已知系统事件，再按 60 分钟切分。对于没有 `event_origin` 的旧合成数据，它只接受白名单中的业务事件，并在报告中明确这仍是兼容性近似。

## 7. 单特征评价框架

每个候选特征至少检查：

```text
Definition / Source / Window / Available-at / Owner
覆盖率与缺失率
黑白及未标记分布
分箱 Bad Rate 和样本支持度
AUC / KS / IV / Lift@业务深度
方向一致性
跨时间 PSI 和漂移
对异常值、账户角色和渠道的敏感度
```

指标分工：

- **IV**：单变量的信息量和分箱区分能力；
- **KS**：模型对整体样本的分层能力；
- **Lift**：某个实际审核或拒绝深度下的抓坏效率。

KS 更高不代表实际 Top 5% 或 Top 10% 审核深度的 Lift 一定更好。策略选择必须以真实运营点位为准。

## 8. 黑用户全链路与案例分析

材料建议挑选少量已确认黑用户，逐个检查：

```text
注册 → KYC → 法币入金 → 现货/闪兑 → 内部转账
→ 链上出金 → 活跃时间 → Web/App/API → 设备/IP/地址关系
```

案例分析的作用是发现机制与候选特征，不是直接证明总体规律。每个小样本发现都必须进入大盘验证：

- 黑白覆盖率；
- 分箱坏率；
- 跨时间稳定性；
- 合法困难负样本；
- 是否由数据缺失或调查选择造成。

---

## 9. 链上地址与 Risk Graph

链上分析应回答：

- 充值/提现地址是否命中 Scam、Gambling、Darknet、Mixer、Stolen Funds 等标签；
- 出金目的地是 Exchange、Private 还是 Unknown；
- 多用户是否共享强关系标识；
- 从已确认黑用户出发，有限 Hop 内是否存在可解释关联路径；
- 公共 IP、交易所归集地址和超级节点是否已过滤。

“Fraud 用户更偏好私人地址”在原材料中是调查假设，不是已经确认的普遍结论。目标地址类型必须作为可审计字段进行验证，不能预设风险方向。

图谱证据的推荐强弱：

- 强关系：KYC ID、设备、手机号、邮箱、提现地址；
- 弱关系：IP，尤其是公共网络和企业代理；
- 需要降噪：Exchange collection、公共 IP、supernode、短期临时标识。

图谱输出只形成候选队列和路径解释，不直接给出身份同人或 Fraud 结论。

## 10. 决策树：用于找规则组合，不追求深树表现

### 原理

分类树每次选择能最大降低节点不纯度的变量和切分点；`max_depth`、`min_samples_leaf` 等约束决定其可解释性和过拟合风险。

### 项目中的用途

```text
候选特征
→ 浅层 Tree
→ 提取路径和阈值
→ 检查叶节点样本量、Fraud Rate、风险倒序和误伤
→ 跨时间验证
→ 稳定路径转为候选 Rule DSL
```

材料中的一版 Recall 导向 Tree 能把 Recall 提高到 80% 以上，但 Precision 约 36.6%，误杀超过一千名正常用户。这说明“召回高”不能单独作为上线依据。

面试表述：

> 我们把浅层决策树作为可解释的交互发现工具，而不是直接把全量深树上线。每条路径都要检查叶节点支持度、风险梯度、误伤、时间稳定性和与现有策略的增量贡献，最后只把稳定路径转成模拟规则。

## 11. XGBoost：做非线性排序和阈值权衡

### 原理

XGBoost 通过逐轮增加树来拟合前序模型的残差/梯度，并利用学习率、行列采样、树深、L1/L2 正则等控制复杂度。它适合处理金额、速度、比例、计数及交互关系的非线性组合。

### 材料中的实验设计

原材料比较过：

```text
负正样本比例：1:3 / 1:4 / 1:5
max_depth：3 / 4 / 5 / 6
概率阈值：0.5 / 0.6 / 0.7 / 0.8 / 0.9
```

因此，`1:4` 不是先验规则，而只是候选之一。材料还指出 depth=6 容易过拟合；提高阈值会提高 Precision，但会放弃更多 Fraud 用户。

当前固定 Demo 为保持确定性复现，仍保留折内 1:4 和随机 Stratified OOF；source-aligned 层明确声明：

1. 下一阶段在 Development 比较自然分布、1:3、1:4、1:5；
2. 最终在时间切分、自然分布 OOT 上报告指标；
3. 欠采样改变先验比例，模型分必须校准后才可解释为概率；
4. 高分 `label=0` 需要进入人工复核，不能直接判定为 False Positive。

### 特征重要性解释

Gain/Weight 重要性只说明模型使用频度或损失贡献，不代表因果。应结合：

- 单变量方向和分箱；
- Permutation Importance；
- SHAP；
- 特征族消融；
- 跨时间稳定性；
- 业务机制与数据可用时间。

## 12. LightGBM 的正确边界

参考材料中能确认的是 Decision Tree 和 XGBoost，没有证据表明原团队在该专项中实际使用了 LightGBM。因此面试中应说：

> LightGBM 是我为公开合成项目补充的可选高维稀疏基线，不是原报告已经上线或验证的模型。

当加入大量事件窗口、行为 N-gram、币对稀疏特征和图谱统计后，可比较 LightGBM 的训练效率；但必须与 XGBoost 使用相同标签、时间切分、审核容量和 OOT 分布。

## 13. 从模型到策略

模型不是最终动作。候选策略至少写清：

```text
Event
Population
Window
Feature Contract
Threshold
Exclusion
Action
Reason Code
Owner
Simulation / Approval / Rollback
```

推荐分层：

- 高分 + 强链上/图谱证据：人工调查、RFI 或增强审核；
- 中风险：T+1 离线名单、持续监控；
- 单一弱信号：仅 Shadow，不自动处置；
- 高影响动作：始终需要人工批准和审计留痕。

上线前后需要：

1. 1:1 历史回溯或 Simulation；
2. 与现有策略做 Overlap、Swap-in、Swap-out；
3. 第二人复核；
4. 上线后监测命中量、Precision、Recall、用户投诉和漂移；
5. Retain / Tune / Pause / Retire 生命周期决策。

AI 的职责只能是提出候选、生成解释和辅助材料；指标、规则解析和状态机由确定性代码执行；人类拥有最终处置权。

## 15. 面试版项目总结

> 我先复盘现有 Fraud 策略的混淆矩阵和审核容量，发现核心矛盾是 Recall 低。随后重新定义黑、白和未标记样本，避免把全部 label=0 当正常，并排除内部、做市商和机构账户。分析按注册/KYC、法币入金、现货或闪兑、链上出金、设备/IP/地址和行为序列展开，构造资金闭环 CV、金额差异率、时间差、计数和关系特征。单特征按覆盖、AUC、KS、IV、Lift 和稳定性评价；浅层 Tree 用于提取可解释组合，XGBoost 用于全量排序，Risk Graph 用于补充关联路径。最后不直接自动处置，而是结合现有策略重叠、审核容量、Simulation 和人工复核，把结果转成线上或离线候选策略。

### 面试追问应主动说明

- 1:4 是候选实验，不是固定最佳比例；
- 随机 OOF 不是时间 OOT；
- 欠采样分数未经校准不能称 Fraud 概率；
- 标签可能延迟成熟，高分未标记不一定是误报；
- API、夜间、单一币对都没有普适风险方向；
- 图谱关系是调查证据，不是身份结论；
- 公开仓库使用的是合成数据，不能冒充生产效果。
